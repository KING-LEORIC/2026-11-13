# LLM 답변 실패 유형 분석 및 검증 보고서

본 보고서는 `main.py` 및 `analysis.py`를 통한 LLM 답변 검증 실습 실행 결과와 `review.json`, `review.md`에 정의된 데이터를 바탕으로, LLM 답변의 실패 유형 분류, 대응 방안, 보안 원칙 및 플랫폼 아키텍처 연계 구조를 종합하여 정리한 문서입니다.

---

## 1. 실행 개요 및 콘솔 출력 결과

* **실행 진입점**: `main.py` (`analysis.py` 내 `run_analysis()` 함수 호출)
* **콘솔 출력**:
  ```text
  [07] [('F01', 'factual_mismatch'), ('F02', 'format'), ('F03', 'evidence')]
  ```
* **요약**: 사전 정의된 3가지 수업용 테스트 케이스(`F01`, `F02`, `F03`)를 대상으로 규칙 기반 검증을 수행한 결과, 각각 사실 불일치, 형식 누락, 근거 누락으로 정확히 분류되었습니다.

---

## 2. 사례별 실패 유형 분류 및 상세 분석

| 사례 ID | 질문 (Question) | 원본 (Source) | 답변 (Answer) | 분류 결과 (Kind) | 실패 원인 및 설명 |
| :---: | :--- | :--- | :--- | :---: | :--- |
| **F01** | 파일을 어디에 보관하나요? | 실습 파일은 개인 폴더에 보관합니다. | 실습 파일은 공용 서버 폴더에 보관합니다. | `factual_mismatch` | **사실 불일치**: 생성된 답변의 주장 내용이 승인된 원본 데이터와 모순됩니다. |
| **F02** | 서버는 어디에서 실행하나요? | 프로젝트 폴더에서 서버를 실행합니다. | 프로젝트 폴더에서 서버를 실행합니다. | `format` | **형식 누락**: 응답 구조 내에 필수 필드(`sources`)가 누락되어 있습니다. |
| **F03** | 질문할 때 무엇을 함께 적나요? | 오류 메시지와 시도한 작업을 함께 적습니다. | 오류 메시지와 시도한 작업을 함께 적습니다. | `evidence` | **근거 누락**: `sources` 필드는 존재하지만 인용된 근거 목록이 비어 있습니다(`[]`). |

## 3. 검증 항목별 정의 및 대응 방안 (Mitigation)

LLM 응답의 신뢰성과 안정성을 확보하기 위해 사실성, 형식, 근거 검증은 각각 독립적인 규칙으로 처리되어야 합니다.

* **형식 검증 (`format`)**
  * **정의**: JSON 및 응답 구조 내에 필수 필드가 올바르게 존재하는지 확인하는 구조 검증
  * **대응 방안**: API 응답 Schema 검증 및 구조화된 출력(Structured Output) 재시도 로직 적용
* **근거 검증 (`evidence`)**
  * **정의**: 인용 및 출처 정보가 포함되어 있는지, 그리고 답변을 뒷받침하기에 적절한 근거인지 구분하는 검증
  * **대응 방안**: RAG(Retrieval-Augmented Generation) 시스템을 통한 관련 문서 검색 및 출처 유효성 검증
* **사실 불일치 검증 (`factual_mismatch`)**
  * **정의**: 모델의 주장(Answer)이 승인된 정답 및 원본(Source) 데이터와 모순되는지 검증
  * **대응 방안**: 승인된 원본 데이터셋과의 명시적 대조 및 교차 검증 규칙 적용

## 4. 추가 점검 항목 및 보안 원칙 (Security & Trust Boundary)

### 가. 추가 점검 항목 (`checks`)
단순한 일치 여부를 넘어 실제 운영 환경에서는 다음과 같은 심층 점검이 필요합니다.
1. **출처 유효성**: 출처 ID가 실제 원문 데이터를 정확하게 가리키고 있는가?
2. **최신성**: 인용된 근거 및 원문 데이터가 최신 상태를 유지하고 있는가?
3. **인덱스 동기화**: 원본 데이터가 변경되었을 때 검색 인덱스(Search Index)도 함께 갱신되었는가?

### 나. 에이전트 도구 권한 제어 (`agent_case`)
* **대상 도구**: `DELETE /api/knowledge/{knowledge_id}`
* **승인 여부**: `approved: false` (미승인 상태)
* **위험 등급**: `unauthorized_tool_write` (권한 없는 쓰기/삭제 작업 위험)
* **조치 원칙**: 위험한 쓰기/삭제 도구 요청은 모델의 판단만으로 즉시 실행하지 않고, 사용자 승인 및 권한 확인 절차를 거칩니다.

### 다. 신뢰 경계 원칙 (`trust_rules`)
1. **외부 데이터 처리**: 검색된 문서 본문이나 외부 텍스트 내의 명령문은 신뢰할 수 없는 데이터(Untrusted Data)로 취급합니다.
2. **권한 분리**: 도구 실행 권한은 모델이 아닌 애플리케이션 계층에서 엄격하게 확인합니다.
3. **투명한 기록**: 원문, 모델의 응답, 검증 결과 과정을 보안 침해 없이 명확하게 로깅하고 기록합니다.

## 5. 플랫폼 아키텍처 연계

본 실습 결과와 향후 후속 수업 간의 플랫폼 컴포넌트 연결 구조는 다음과 같습니다.

* **FastAPI**: 클라이언트와 서버 간의 엄격한 입력·출력 계약(Schema) 검증 담당
* **PostgreSQL**: 원본 지식 데이터 및 분류 체계의 관계형 저장 담당
* **RAG 계층**: 질문에 부합하는 관련 근거 문서 검색 및 출처 매칭 담당
* **Agent 계층**: 외부 도구 호출 시 권한 확인 및 승인 제어 담당

## 7. 결론

생성형 AI와 LLM을 프로덕션 환경에 도입할 때 가장 흔하게 범하는 오류는 **"모델의 자연스러운 언어 구사 능력을 곧 신뢰성과 사실성의 보증으로 오인하는 것"**입니다. 이번 실습을 통해 확인할 수 있듯, LLM은 확률적으로 다음 토큰을 예측하는 생성 엔진일 뿐, 스스로 데이터의 진위나 구조적 규격을 보장하지 못합니다.

따라서 성공적인 AI 애플리케이션 구축을 위해서는 다음 세 가지 엔지니어링 원칙이 필수적입니다.
1. **방어적 프로그래밍과 결정론적 가드레일**: 모델의 출력에만 의존하지 않고, FastAPI와 같은 백엔드 계층에서 Schema 검증 및 구조화된 출력을 강제해야 합니다.
2. **엄격한 신뢰 경계(Trust Boundary) 설정**: 검색된 외부 문서나 사용자 입력 내의 악의적 지시어가 시스템 권한으로 승격되지 않도록 데이터와 명령을 철저히 분리해야 합니다.
3. **도구 실행의 권한 분리**: 에이전트가 데이터 수정이나 삭제(`DELETE`) 같은 파괴적인 작업을 수행할 때는 반드시 애플리케이션 레벨의 사전 승인 단계를 거치도록 설계해야 합니다.

결론적으로, LLM의 한계를 명확히 이해하고 이를 구조적 검증 규칙과 보안 아키텍처로 보완하는 것이 안정적인 AI 지식 플랫폼을 만드는 핵심 열쇠입니다.
